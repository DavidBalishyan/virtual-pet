# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Tamagotchi-style virtual pet firmware for the M5StickC Plus 2 (ESP32), written as
a teaching project across a 10-session embedded C++ course. It is a PlatformIO /
Arduino project. See `README.md` for the gameplay and hardware summary.

## Commands

The `Makefile` wraps PlatformIO. `pio` is run via `pipx run platformio` by default.

```bash
make build        # Compile firmware for the device (env: m5stick-c). Runs `generate` first.
make upload       # Build + flash to a connected device
make run          # upload + serial monitor
make monitor      # Serial monitor (115200 baud); MONITOR_PORT=/dev/... to pin a port
make test         # Run host unit tests (env: native)
make lint         # cppcheck (c++17, warning/style/performance/portability)
make format       # clang-format -i (style from .clang-format)
make clean        # Remove build artifacts + generated files for the env
make generate     # Regenerate dashboard + sprite asset headers only
```

Target a different board/test env with `make build ENV=...` / `make test TEST=...`.

Run a **single test suite** with a PlatformIO filter (bypass the Makefile):

```bash
pio test -e native -f test_pet          # only test_pet
pio test -e native -f test_tilt_motion
```

## Two build environments (platformio.ini)

- `m5stick-c` — the real firmware. Compiles everything under `src/` and `lib/`.
  Feature set is controlled by `lib/Config/scaffold_config.h` (see below).
- `native` — host unit tests. Compiles selected `lib/` modules on your PC against
  the stub `test/stubs/Arduino.h` using the Unity framework. **Its enabled features
  are hardcoded in `platformio.ini` build_flags** (`ENABLE_ACTION_MENU`,
  `ENABLE_SOUND`, `ENABLE_MULTISCREEN`, `ENABLE_MOOD_SPRITES`) — NOT read from
  `scaffold_config.h`. If you add a test that depends on a different flag, add it
  to the native `build_flags`.

PlatformIO only compiles `src/` and `lib/`. `tools/` holds host-side Perl scripts
(never flashed) — do not move them into `src/`/`lib/`.

## Feature switches — the central concept

`lib/Config/scaffold_config.h` defines `ENABLE_*` macros. The project is a
*cumulative curriculum*: each course session turns on one more feature, and every
major feature is wrapped in `#ifdef`. On `main` (the finished reference) all
switches are on; session branches comment some out to recreate earlier stages.

Consequences when editing:
- **Every file that uses a feature `#include`s `scaffold_config.h`** so all
  translation units agree on which features exist. A bare `#define` in `main.cpp`
  is invisible to `pet.cpp` etc. — that is why the switches live in a shared header.
- Function signatures change with flags. Methods like `Pet::updateState(...)`,
  `Pet::reset(...)`, and `ActionMenu::confirmAction(...)` take a `SpeakerManager&` /
  `StorageManager&` **only when the relevant flag is on**. When editing these, keep
  the `#ifdef` blocks around both the declaration and every call site in sync.
- There are guard rails: an impossible combination (`ENABLE_PERSISTENCE` without
  `ENABLE_ACTION_MENU`) fails the build with an `#error`.

## Generated files (do not edit, do not commit)

Two headers are generated by Perl scripts and are gitignored:
- `lib/Wireless/dashboard_assets.h` — the web dashboard's HTML/CSS/JS embedded as
  C strings, produced by `tools/embed_file.pl` from `lib/Wireless/dashboard.{html,css,js}`.
- `lib/Display/sprites/*.h` — sprites converted from `assets/sprites/raw/*.c` by
  `tools/convert_sprites.pl`.

`make build` depends on `generate`, so a normal build recreates them. If you edit
the dashboard front-end or a sprite, rerun `make generate` (or `make build`). A
fresh clone will not have these files until the first build.

## Architecture

`src/main.cpp` is the only file with `setup()`/`loop()`. It owns one global
instance of each manager and wires them together. The loop is a short outline:
**read inputs → update pet/state → render**. Everything else is a single-purpose
manager under `lib/<Name>/`:

- `Pet` (`lib/Pet`) — the domain model. Holds all stats (0–100), the `PetState`
  machine, care actions (`feed`/`play`/`sleep`/`bathe`/`heal`/`drink`), `computeMood()`,
  and death/reset. No hardware knowledge. This is the most-tested module.
- `TimerManager` (`lib/Timer`) — all automatic stat decay rules over time. The pet's
  stats only change on their own here.
- `DisplayManager` (`lib/Display`) — all rendering. Draws to an off-screen `M5Canvas`
  and pushes the whole frame once (no flicker). `screen_layout.h` holds zone geometry
  and the `MoodSprite` / `RelevantStat` / `ScreenState` enums.
- `NavigationManager` (`lib/Navigation`) — owns which `ScreenState` is active and
  routes button input per screen.
- `ActionMenu`, `ButtonHandler`, `ImuManager` + `TiltMotion`, `SpeakerManager`,
  `StorageManager` (NVS flash), `ClockManager` (RTC), `WirelessManager` (WiFi AP +
  web dashboard + WebSocket) — each owns exactly one subsystem.

**Key decoupling rule (follow it when extending):** managers pass *primitive values*
across boundaries, not each other's objects. `DisplayManager::renderDisplay()` takes
ints/strings/enums, so it does not know what a `Pet` or `ActionMenu` is;
`NavigationManager` receives a plain `bool backSelected` rather than the menu. When
adding a cross-module interaction, extract the needed values in `main.cpp` and pass
them in rather than handing over a whole manager.

### Extension seams (documented in-code)
- **Add a stat**: see the comment block at the top of `Pet`'s private section in
  `lib/Pet/pet.h` — it lists every file that must change (field + getter/setter +
  `DEFAULT_`; decay rule in `time_manager.cpp`; `RelevantStat` + a
  `drawContextualStatBar` case; a care action).
- **Add a mood**: add a case to `spriteForMood()` in `display_manager.cpp`.

## Tests

`test/test_*/test_*.cpp` compile the **real** `lib/` sources (not mocks) against
`test/stubs/Arduino.h`, which provides a deterministic `millis()` via `setMillis()`.
To add a suite: create `test/test_your_module/test_your_module.cpp`, include the
module's `.h` with a relative path, add any needed hardware stub under `test/stubs/`,
and (if it needs a feature flag) add that flag to the `native` build_flags. See
`test/README.md`.
